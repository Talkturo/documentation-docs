## Build on the Talkturo API

Build integrations and automations on top of Talkturo's voice AI platform with a REST API for assistants, telephony, phone numbers, credits, CRM data, workflows, and account management. Use this page to understand the API's core conventions and find the endpoint group you need.

<Callout kind="info" collapsed="false">
  Send API requests to your deployment's origin followed by `/api`. Talkturo does not define a single production hostname or `/v1` base path in the API implementation.
</Callout>

## Authenticate requests

Shared routes can accept API keys, session bearer tokens, or authenticated cookies, but individual routes do not necessarily support every authentication method. Check [Authentication](/en/api-reference/authentication) and the specific endpoint reference before choosing an authentication flow.

<Tabs>
  <Tab title="API keys" icon="key">
    Use a bearer token that starts with `tk_live_` or `tk_test_` for server-to-server requests. Authentication behavior can vary by route, so review the endpoint reference and [Authentication](/en/api-reference/authentication) for supported credentials.

    API-key creation includes a `rate_limit_per_hour` value that defaults to `1000`. Do not treat that field as a globally enforced request limit.
  </Tab>

  <Tab title="Session cookies" icon="lock">
    The Talkturo web app uses authenticated session cookies for browser-based requests. This method is intended for first-party web sessions, not external backend integrations.

    See [Authentication](/en/api-reference/authentication) for when session-based authentication applies.
  </Tab>

  <Tab title="JWT bearer tokens" icon="monitor">
    Session-based clients can use bearer JWT tokens for authenticated API access. The routes that accept this method vary by endpoint.

    See [Authentication](/en/api-reference/authentication) and [Desktop Auth](/en/api-reference/desktop) for details.
  </Tab>
</Tabs>

## Understand endpoint-specific responses

Talkturo does not apply one response envelope or error schema to every endpoint. Individual routes can return different response bodies and HTTP statuses, so use the reference page for the endpoint you are calling instead of assuming that every response contains a `success` field.

The API-key diagnostic endpoint is one documented example. Call `GET /api/test-api-key` with a valid API key to verify authentication and inspect the authentication context returned by that route.

<Request show-lines="true">
  ```http
  GET /api/test-api-key
  Authorization: Bearer tk_live_example_9xmk7q2r
  ```

</Request>

<Response show-lines="false">
  ```json
  {
    "success": true,
    "message": "Authentication successful!",
    "authMethod": "api_key",
    "accountId": "acc_7f31c9e2",
    "userId": "usr_a1b2c3d4",
    "apiKeyId": "key_4e8f2a1c",
    "timestamp": "2025-01-15T14:30:00.000Z"
  }
  ```

</Response>

### Handle HTTP status codes

Status codes vary by endpoint. Check the status codes documented on the reference page for the route you are calling, then inspect that endpoint's response body for details your application can log or surface.

| Status | Meaning              |
| ------ | -------------------- |
| `200`  | Request succeeded    |
| `201`  | Resource created     |
| `400`  | Bad request          |
| `401`  | Unauthorized         |
| `402`  | Insufficient credits |
| `403`  | Forbidden            |
| `404`  | Not found            |
| `500`  | Server error         |

## Plan for rate limits

Do not assume a global API-key rate limit. API-key creation includes a `rate_limit_per_hour` value that defaults to `1000`, but the checked-in API code does not establish that value as a globally enforced limit.

If an endpoint documents a limit, add backoff and retry handling to background jobs, retries, or bulk syncs so your integration handles that endpoint's behavior gracefully.

## Start with the most common integration path

Most external developers begin with API keys, then move into assistants, telephony, or CRM endpoints depending on the product they are building. If you are setting up a new integration, read [Authentication](/en/api-reference/authentication) first, then continue to the resource-specific reference page for your use case.
