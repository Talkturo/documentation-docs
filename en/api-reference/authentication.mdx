## Authenticate requests

Authenticate shared Talkturo API routes with a **Talkturo API key**, a **Supabase bearer session token**, or a **browser session cookie**. API keys identify the account associated with the key, Supabase bearer tokens require an `accountSlug` query parameter, and cookie-based requests use `accountSlug` or `teamId` from the query or request body when the route supports it.

### Authentication methods at a glance

| Method | Best for | How to send it |
| --- | --- | --- |
| API key | Server-to-server integrations and external apps | `Authorization: Bearer tk_live_...` or `Authorization: Bearer tk_test_...` |
| Supabase bearer session token | Shared API routes called with an authenticated user session | `Authorization: Bearer eyJhbGciOi...` with `accountSlug` in the query |
| Session cookie | Requests made from the Talkturo web app | No `Authorization` header; browser sends the httpOnly cookie automatically |
| Desktop authentication | Desktop app route family | Supabase bearer token on desktop-specific routes |

API-key management endpoints use Supabase bearer session tokens and never accept Talkturo API keys. Desktop authentication is also a separate route family, not a general authentication method for every API endpoint.

## API key authentication

Send your Talkturo API key in the `Authorization` header as a bearer token. Talkturo accepts keys with both `tk_live_` and `tk_test_` prefixes from the same key store. The prefix does not establish a separate environment.

<CodeGroup tabs="cURL">

```bash
curl -X GET "https://api.talkturo.com/api/test-api-key" \
  -H "Authorization: Bearer tk_live_example_9xmk7q2r8f4c1v6n3p7s2d5h8j1k4m6q9w2e5r8t1y4u7"
```

</CodeGroup>

Talkturo securely validates the submitted key and checks it against the stored key record. The key grants access within the account associated with it. Routes that define scope requirements check those scopes during authentication, while other routes may only validate the key and its account.

If a request includes an invalid `tk_` API key, Talkturo returns `401` and does not fall back to a session cookie.

<Callout kind="alert">

Treat API keys like passwords. Store them in a secret manager or environment variable, send them only over HTTPS, and never expose them in client-side code, public repositories, or browser storage.

</Callout>

### API key format

API keys use one of these prefixes:

- **`tk_live_`**: live key prefix
- **`tk_test_`**: test key prefix

Both prefixes use the same key store and authentication flow. A key is returned only once when you create it. Talkturo stores only a SHA-256 hash of the full key, so you cannot retrieve the plaintext value later.

## Scope system

Scopes control access on routes that define scope requirements. A key can allow everything, a namespace of related operations, or a specific permission string.

<ParamField body="*" param-type="scope string" required="false" show-location="false">

Default full-access scope for routes that use scope checks. Grants access to all scopes supported by those routes.

</ParamField>

<ParamField body="prefix:*" param-type="scope string" required="false" show-location="false">

Wildcard prefix scope. Grants access to every scope that starts with the same prefix. For example, `assistants:*` matches assistant-related scopes in that namespace.

</ParamField>

<ParamField body="specific scope" param-type="scope string" required="false" show-location="false">

Exact-match scope. Grants access only when the required scope string matches exactly.

</ParamField>

<ParamField body="rate_limit_per_hour" param-type="integer" required="false" show-location="false">

Hourly request limit stored as metadata on the key permissions. Newly created keys default to `1000`. Talkturo's shared API authentication stores this value but does not enforce it; individual endpoints may apply their own limits.

</ParamField>

When a route uses scope checks, Talkturo checks scopes in this order: full wildcard, prefix wildcard, then exact match. Newly created API keys default to the `*` scope unless you set a narrower permission set.

## Dual-auth mode

Some Talkturo API routes support API keys and authenticated browser sessions through shared API authentication. These routes also support a non-`tk_` Supabase bearer session token when the request includes `accountSlug` in the query.

<Callout kind="info">

Dual-auth routes choose the authentication method from the request. A valid Talkturo API key authenticates the request for the account associated with that key. Without an `Authorization` header, a supported browser session cookie can authenticate the request when the route receives `accountSlug` or `teamId` from the query or request body. An invalid `tk_` API key returns `401` and does not fall back to the cookie.

</Callout>

This behavior lets supported endpoints work for external integrations and requests made from the Talkturo web app. Route-specific scope checks still apply only where the route defines them.

## Session cookie authentication

Session cookie authentication is the standard browser flow for the Talkturo web app. After a user signs in, Supabase stores the authenticated session in an httpOnly cookie, and browser requests to session-protected routes send that cookie automatically.

Do not send an `Authorization` header when you want a supported route to use the browser session cookie. Include `accountSlug` or `teamId` in the query or request body when the route requires one.

Use session cookies when your code runs inside the web app context. For external integrations, use API keys instead.

## Supabase bearer token authentication

Shared API routes can accept a Supabase access token in the `Authorization` header when the token is not a Talkturo `tk_` API key. Include `accountSlug` in the query so the route can resolve the account for the request.

<CodeGroup tabs="cURL">

```bash
curl -X GET "https://api.talkturo.com/api/test-api-key?accountSlug=acme" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c3JfYTFiMmMzZDQiLCJlbWFpbCI6ImphbmVAYWNtZS5jb20ifQ.desktop_example_token"
```

</CodeGroup>

API-key management endpoints require this Supabase bearer session token. They do not accept a Talkturo API key.

## Desktop authentication

Desktop app routes form a separate route family and accept a Supabase access token in the `Authorization` header. Talkturo validates the token with Supabase for the presented bearer token.

<CodeGroup tabs="cURL">

```bash
curl -X POST "https://api.talkturo.com/api/auth/sign-out" \
  -H "Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiJ1c3JfYTFiMmMzZDQiLCJlbWFpbCI6ImphbmVAYWNtZS5jb20ifQ.desktop_example_token"
```

</CodeGroup>

Desktop routes also support cross-origin requests and handle `OPTIONS` preflight requests. Use this method only for desktop app flows that already manage Supabase user sessions.

## Test authentication

Call `GET /api/test-api-key` to confirm that your Talkturo API key is valid and accepted by the endpoint. This endpoint uses the API-key authentication flow and does not represent the requirements of every API route.

<Request tabs="cURL" default-tab="1">

```bash
curl -X GET "https://api.talkturo.com/api/test-api-key" \
  -H "Authorization: Bearer tk_test_example_4f7a9c2d8m1q5r6s3t9v2w4x7y1z8b5n6p3k9h2j4u6"
```

</Request>

<Response tabs="200,401" default-tab="1">

```json
{
  "success": true,
  "message": "Authentication succeeded"
}
```

```json
{
  "success": false,
  "error": "Invalid API key"
}
```

</Response>

A successful response confirms that the key is active and accepted by this endpoint. If the request fails, verify the bearer token format, key prefix, key status, and any scope requirements defined by the route.
