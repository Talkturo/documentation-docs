## Anfragen authentifizieren

Gemeinsam authentifizierte Talkturo-API-Routen akzeptieren drei Authentifizierungswege: **Talkturo-API-Schlüssel**, **Supabase-Bearer-Sitzungstoken** oder **Browser-Sitzungs-Cookies**. API-Schlüssel identifizieren das Konto direkt. Sitzungstoken benötigen `accountSlug` in der Query, und Cookie-Anfragen benötigen je nach Route `accountSlug` oder `teamId` in der Query oder im Request-Body. Die Desktop-Authentifizierung gehört zu einer separaten Routengruppe und ist kein allgemeiner API-Login.

### Authentifizierungsmethoden auf einen Blick

| Methode | Am besten geeignet für | So senden Sie sie |
| --- | --- | --- |
| API-Schlüssel | Server-zu-Server-Integrationen und externe Apps | `Authorization: Bearer tk_live_...` oder `Authorization: Bearer tk_test_...` |
| Sitzungs-Cookie | Anfragen aus der Talkturo-Web-App | Automatisches httpOnly-Cookie |
| JWT-Bearer-Token | Anfragen aus der Desktop-App | `Authorization: Bearer eyJhbGciOi...` |

## Authentifizierung mit API-Schlüsseln

Senden Sie Ihren API-Schlüssel im `Authorization`-Header als Bearer-Token. Talkturo akzeptiert die Präfixe `tk_live_` und `tk_test_` über denselben Schlüsselspeicher; sie bilden keine getrennten Authentifizierungsumgebungen.

Talkturo prüft, ob der Schlüssel gültig, aktiv und nicht abgelaufen ist. Die Route führt zusätzlich nur dann eine Scope-Prüfung durch, wenn sie bestimmte Scopes verlangt.

### Format von API-Schlüsseln

API-Schlüssel verwenden eines dieser Präfixe:

- **`tk_live_`** — Live-Schlüssel
- **`tk_test_`** — Testschlüssel

Beide Präfixe werden über denselben Schlüsselspeicher geprüft und bilden keine getrennten Authentifizierungsumgebungen. Ein Schlüssel wird nur einmal zurückgegeben, wenn Sie ihn erstellen. Talkturo speichert nur einen SHA-256-Hash des vollständigen Schlüssels, daher können Sie den Klartextwert später nicht erneut abrufen.

## Scope-System

Scopes steuern, welche Operationen ein API-Schlüssel ausführen darf. Ein Schlüssel kann alles erlauben, einen Namespace verwandter Operationen oder einen bestimmten Berechtigungs-String. Scopes werden nur von Routen geprüft, die Scope-Anforderungen definieren. Das gespeicherte Metadatum `rate_limit_per_hour` erzwingt kein allgemeines Limit für API-Schlüssel; einzelne Endpunkte können eigene Limits haben.

## Gemeinsam authentifizierte API-Routen

Gemeinsam authentifizierte Routen akzeptieren mehrere Anmeldeinformationen, wählen den Authentifizierungsweg aber anhand der übermittelten Daten. Verwenden Sie den Weg, der zu Ihrem Aufrufer passt.

- **Talkturo-API-Schlüssel:** Senden Sie `Authorization: Bearer tk_live_...` oder `Authorization: Bearer tk_test_...`. Das Konto stammt aus dem API-Schlüssel.
- **Supabase-Bearer-Sitzungstoken:** Senden Sie ein Bearer-Token, das nicht mit `tk_` beginnt, und geben Sie `accountSlug` in der Query an.
- **Browser-Sitzungs-Cookie:** Lassen Sie den `Authorization`-Header weg und senden Sie das authentifizierte Sitzungs-Cookie. Geben Sie `accountSlug` oder `teamId` in der Query oder im Request-Body an, sofern die Route diesen Parameter unterstützt.

Ein ungültiger `tk_`-Schlüssel gibt `401` zurück und fällt nicht auf ein Sitzungs-Cookie zurück. API-Schlüssel-Verwaltungsendpunkte bilden eine Ausnahme: Sie benötigen ein Supabase-Bearer-Sitzungstoken und akzeptieren keine Talkturo-API-Schlüssel.

## Authentifizierung mit Sitzungs-Cookies

Die Authentifizierung mit Sitzungs-Cookies ist der Browser-Flow für gemeinsam authentifizierte Talkturo-API-Routen. Lassen Sie den `Authorization`-Header weg, damit der Browser das authentifizierte httpOnly-Sitzungs-Cookie automatisch sendet. Geben Sie zusätzlich `accountSlug` oder `teamId` in der Query oder im Request-Body an, sofern die Route diesen Parameter unterstützt.

Verwenden Sie für externe Integrationen API-Schlüssel. Ein ungültiger `tk_`-Schlüssel wird nicht durch das Sitzungs-Cookie ersetzt.

## Authentifizierung mit JWT-Bearer-Token

Routen der Desktop-App akzeptieren ein Supabase-Access-Token im `Authorization`-Header. Diese Desktop-Authentifizierung gehört zu einer separaten Routengruppe und dient nicht als allgemeiner API-Login für gemeinsam authentifizierte Routen.

Desktop-Routen unterstützen außerdem Cross-Origin-Anfragen und verarbeiten `OPTIONS`-Preflight-Anfragen. Verwenden Sie diese Methode nur für Desktop-App-Flows, die bereits Supabase-Benutzersitzungen verwalten.

## Authentifizierung testen

Rufen Sie `GET /api/test-api-key` auf, um zu bestätigen, dass Ihre Anmeldeinformationen gültig sind und von Talkturo akzeptiert werden. Dieser Endpunkt verwendet denselben Authentifizierungs-Flow wie andere Routen mit API-Schlüssel-Unterstützung.

Eine erfolgreiche Antwort bestätigt, dass der Schlüssel aktiv, nicht abgelaufen und durch die Scope-Prüfung zugelassen ist. Wenn die Anfrage fehlschlägt, prüfen Sie das Format des Bearer-Tokens, das Umgebungspräfix des Schlüssels, den Schlüsselstatus und die Scope-Konfiguration.

<Request tabs="cURL,JavaScript" default-tab="1">
```bash
curl -X GET "https://api.talkturo.com/api/test-api-key" \
  -H "Authorization: Bearer tk_test_example_9xmk7q2r"
```

```javascript
const response = await fetch("https://api.talkturo.com/api/test-api-key", {
  method: "GET",
  headers: {
    Authorization: "Bearer tk_test_example_9xmk7q2r",
  },
});

const data = await response.json();
console.log(data);
```
</Request>

<Response tabs="200,401" default-tab="1">
```json
{
  "success": true,
  "message": "API key is valid",
  "authType": "api_key"
}
```

```json
{
  "success": false,
  "error": "Invalid API key"
}
```
</Response>
