## Entwickeln Sie auf der Talkturo API

Erstellen Sie Integrationen und Automatisierungen auf Basis der Voice-AI-Plattform von Talkturo mit einer REST-API für Assistenten, Telefonie, Telefonnummern, Guthaben, CRM-Daten, Workflows und Kontoverwaltung. Auf dieser Seite lernen Sie die grundlegenden API-Konventionen kennen und finden die Endpunktgruppe, die Sie benötigen.

<Callout kind="info" collapsed="false">
  Senden Sie alle API-Anfragen an den deployment-spezifischen Origin mit dem Suffix `/api`.
</Callout>

## Authentifizieren Sie Anfragen

Talkturo unterstützt mehrere Authentifizierungsmethoden. Gemeinsame Routen können API-Schlüssel, Sitzungs-Bearer-Token oder Sitzungscookies akzeptieren. Welche Methoden unterstützt werden und welche Anforderungen gelten, hängt von der jeweiligen Route ab.

<Tabs>
  <Tab title="API-Schlüssel" icon="key">
    Verwenden Sie ein Bearer-Token, das mit `tk_live_` oder `tk_test_` beginnt, um Server-zu-Server-Anfragen zu authentifizieren. Scopes werden nicht für alle Routen einheitlich erzwungen. Prüfen Sie daher die Authentifizierungsanforderungen auf der jeweiligen Endpunktseite.

    Unter [Authentifizierung](/de/api-reference/authentication) finden Sie das Header-Format und Sicherheitshinweise.
  </Tab>

  <Tab title="Sitzungs-Cookies" icon="lock">
    Die Talkturo-Web-App verwendet authentifizierte Sitzungs-Cookies für browserbasierte Anfragen. Diese Methode ist für Web-Sitzungen der eigenen Anwendung vorgesehen, nicht für externe Backend-Integrationen.

    Unter [Authentifizierung](/de/api-reference/authentication) erfahren Sie, wann sitzungsbasierte Authentifizierung zum Einsatz kommt.
  </Tab>

  <Tab title="JWT-Bearer-Token" icon="monitor">
    Die Desktop-App verwendet Bearer-JWT-Token für authentifizierten API-Zugriff. Dieser Ablauf ist speziell für Desktop-Clients gedacht, die sich über Talkturo-Benutzersitzungen authentifizieren.

    Weitere Informationen finden Sie unter [Authentifizierung](/de/api-reference/authentication) und [Desktop-Authentifizierung](/de/api-reference/desktop).
  </Tab>
</Tabs>

## Antwortformat verstehen

Antwortkörper, Fehlerstrukturen und das Verhalten bei HTTP-Statuscodes sind endpoint-spezifisch. Prüfen Sie die jeweilige Endpunktseite, bevor Sie Antwortdaten oder Fehlerbehandlung implementieren.

### HTTP-Statuscodes

| Status | Bedeutung             |
| ------ | --------------------- |
| `200`  | Anfrage erfolgreich   |
| `201`  | Ressource erstellt    |
| `400`  | Ungültige Anfrage     |
| `401`  | Nicht autorisiert     |
| `402`  | Ungenügendes Guthaben |
| `403`  | Verboten              |
| `404`  | Nicht gefunden        |
| `500`  | Serverfehler          |

Die tatsächlich verwendeten Statuscodes und ihre Bedeutung können je nach Endpunkt variieren. Die Endpunktreferenz enthält die gültigen Antwort- und Fehlerschemas.

## Ratenlimits

Bei der Erstellung eines API-Schlüssels ist das Feld `rate_limit_per_hour` standardmäßig auf `1000` gesetzt. Der vorhandene Code legt nicht fest, dass dieser Wert global für alle API-Schlüssel oder Routen erzwungen wird. Prüfen Sie die Angaben auf der jeweiligen Endpunktseite und implementieren Sie bei Hintergrundjobs, Wiederholungen oder Massensynchronisierungen eine Backoff- und Wiederholungsbehandlung.

## Endpunktgruppen durchsuchen

Beginnen Sie mit der Gruppe, die zur Ressource oder zum Workflow passt, den Sie integrieren möchten. Jede Referenzseite dokumentiert Endpunkte, Authentifizierungsanforderungen sowie Anfrage-, Antwort- und Fehlerschemas.

Die Erstellung von Unternehmen ist veraltet: `POST` gibt für diesen Vorgang den Status `410` zurück. Verwenden Sie stattdessen [CRM Groups](/de/api-reference/crm-groups).

## Mit dem häufigsten Integrationspfad beginnen

Die meisten externen Entwickler beginnen mit API-Schlüsseln und gehen dann zu Assistenten-, Telefonie- oder CRM-Endpunkten über, je nach Produkt.
